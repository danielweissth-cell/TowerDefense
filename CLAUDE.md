# CLAUDE.md: правила проекта Tower Defense (UE5)

Этот файл Claude читает в начале каждой сессии. Здесь правила, которые действуют всегда.
Если правило мешает, его меняют **здесь** (а не обходят молча).

## 0. Перед любой работой
1. Прочитать [PLAN.md](PLAN.md): там текущий этап и что уже сделано (чекбоксы).
2. Прочитать [DECISIONS.md](DECISIONS.md): там принятые решения. **Не пересматривать их** без явной просьбы пользователя.
3. Если задача не вписывается в план или противоречит решению, сначала спросить.

## 1. О пользователе и общении
- Общение **на русском**. Код, имена, комментарии в коде на **английском**.
- Пользователь **новичок в UE5**. Объяснять шаги в редакторе подробно: какое меню, какая кнопка, что выбрать.
  Термины UE давать на английском (как в интерфейсе редактора), с пояснением по-русски.
- Пользователь хочет «сразу правильно». Не делать временных костылей «потом переделаем».
  Если упрощение необходимо, явно сказать и записать в DECISIONS.md.

## 2. Как работаем
- **Сначала план, потом код.** Перед этапом/крупной задачей написать короткий план и дождаться «ок».
- Работаем **маленькими шагами**: один шаг → пользователь компилирует и проверяет в редакторе → коммит → дальше.
- Не делать больше, чем просили. Не трогать несвязанный код «заодно».
- После завершения шага обновить чекбоксы в PLAN.md.
- Новое архитектурное решение → запись в DECISIONS.md.
- Не создавать лишних файлов-документов. Документация проекта это: `CLAUDE.md`, `PLAN.md`, `DECISIONS.md`.

## 3. Архитектура (обязательно)
- **Игра только одиночная.** Никакой репликации (`Replicated`, `Server`/`Client` RPC, `HasAuthority`-логики) не писать.
- **Платформа: телефоны.** Любое решение проверять вопросом «как это будет на телефоне?»:
  управление пальцем, мобильный рендерер (без Lumen/Nanite), производительность, батарея, Safe Zone, размер сборки.
  Ввод делать так, чтобы работал и тач (на телефоне), и мышь (в редакторе для тестов).
- **Классификация через Gameplay Tags** (`Enemy.Air`, `Damage.Fire`, `Status.Slowed`…), не через enum-ы и цепочки `if`.
- **Урон** передаётся только структурой `FTDDamageInfo`, никогда голым `float`.
- Враги/снаряды/эффекты создаются **только через `UTDSpawnSubsystem`**, не прямым `SpawnActor` из игрового кода.
- Для каждой новой механики сразу добавлять средства отладки (чит-команда в `UTDCheatManager`, debug-отрисовка).
- **C++** содержит всю игровую логику и правила. **Blueprints** содержат только внешний вид, звук, визуальные мелочи
  (наследники C++ классов). **UI (UMG)** только отображает и отправляет команды, логики в нём нет.
- **Все числа баланса в Data Assets** (`UTD...Data`). Никаких магических чисел в коде и BP.
- Системы общаются через **делегаты/события**, а не через жёсткие ссылки друг на друга.
  UI подписывается на события GameState, а не опрашивает его в Tick.
- Общие возможности оформлять **компонентами** (`UTDHealthComponent` и т.п.), а не копипастой в классах.
- Глобальные менеджеры делать как **Subsystem** (World / GameInstance), не синглтоны и не «менеджер-акторы» на карте.
- **Tick выключен по умолчанию** (`PrimaryActorTick.bCanEverTick = false`), включать только когда реально нужен.
  Для периодических действий использовать таймеры.
- Враги двигаются по сплайну без `CharacterMovementComponent`.
- Описание объектов в Data Assets, цифры баланса в Data Tables.
- Ввод только через **Enhanced Input**.
- Структура классов и папок как в PLAN.md, раздел 3. Новые папки не выдумывать без причины.

## 3.1 Локализация: английский + русский (обязательно с первого дня)
- Исходный язык **английский**, перевод на русский через стандартную систему UE (Localization Dashboard).
- **Весь текст, который видит игрок, хранится как `FText`.** Никогда не `FString`/`FName` для отображаемого текста.
  `FString` только для логов, путей, отладки.
- Тексты берутся из **String Tables** (`ST_UI`, `ST_Towers`, `ST_Enemies`, `ST_Tutorial`…), а не пишутся прямо в виджетах и Data Assets.
  В C++: `LOCTEXT`/`NSLOCTEXT` или `FText::FromStringTable`. В Data Assets: поля `FText` (имя, описание башни).
- Текст **не склеивается** из кусков (`"Wave " + N`). Только `FText::Format` с именованными аргументами:
  `"Wave {Current} of {Total}"`. В русском другой порядок слов, склейка ломает перевод.
- **Множественное число:** русский язык требует форм one/few/many («1 враг / 2 врага / 5 врагов»).
  Использовать синтаксис плюралов FText: `{Count}|plural(one=enemy,other=enemies)`.
- Числа, проценты, время форматировать через `FText::AsNumber` / `AsPercent` / `AsTimespan`, не вручную.
- **Шрифт обязан поддерживать кириллицу** (проверять при выборе любого шрифта).
- Русский текст примерно на 30% длиннее английского: виджеты **тянутся по содержимому**, а не фиксированной ширины.
  Проверять каждый экран на обоих языках.
- Ключи текстов осмысленные: `Tower.Cannon.Name`, `UI.HUD.Gold`, а не случайные GUID.
- Язык выбирается автоматически по системе, можно сменить в настройках; выбор сохраняется.
- Шрифт интерфейса: `FNT_Rubik` (`Content/TD/UI/Fonts/`, начертания Regular / Medium / Bold). Другие шрифты не добавлять без причины.
- **Обновление переводов** (после любого изменения текстов). Цель локализации `Game`, настройки в `Config/DefaultEditor.ini`,
  сценарии в `Config/Localization/Game_*.ini`. Claude запускает их сам из терминала:
  `"/Users/Shared/Epic Games/UE_5.8/Engine/Binaries/Mac/UnrealEditor-Cmd" "$PWD/TowerDefense.uproject" -run=GatherText -config="Config/Localization/Game_<Gather|Compile|GenerateReports>.ini" -Unattended`
  Порядок: Gather → перевод в `Content/Localization/Game/ru/Game.archive` (UTF-16, править с сохранением кодировки) → Compile → GenerateReports.
  Если настройки цели менялись в `DefaultEditor.ini` при открытом редакторе, перед открытием Localization Dashboard редактор перезапустить,
  иначе он перезапишет файл старыми настройками.

## 4. Стиль C++ (Epic Coding Standard)
- Префикс проекта **`TD`** для всех классов: `ATDTowerBase`, `UTDHealthComponent`, `FTDWaveEntry`, `ETDTargetingMode`.
- Префиксы UE: `A` актор, `U` UObject/компонент, `F` структура, `E` enum, `I` интерфейс, `b` для bool (`bIsDead`).
- Имена: `PascalCase` для всего (типы, функции, переменные). Понятные полные имена, без сокращений (`FireRate`, а не `fr`).
- Один класс = один `.h` + один `.cpp`, имя файла = имя класса без префикса (`TDTowerBase.h`).
- В `.h` минимум `#include`, использовать forward declarations. `#include "X.generated.h"` последним.
- `UPROPERTY` всегда с категорией: `UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "TD|Tower")`.
  - `EditDefaultsOnly` для настроек класса, `VisibleAnywhere` для компонентов, `EditInstanceOnly` только для того, что ставится на уровне.
  - Указатели на UObject: `TObjectPtr<>` в полях класса.
- `UFUNCTION(BlueprintCallable / BlueprintPure / BlueprintImplementableEvent / BlueprintNativeEvent)` только где это реально нужно BP.
- Порядок в классе: `public` → `protected` → `private`; сначала функции, потом поля.
- `const` везде, где можно. Проверки на `nullptr` / `IsValid()` перед использованием.
- Ошибки: `ensure`/`check` для ошибок программиста, `UE_LOG(LogTD, ...)` для логов. Своя категория лога `LogTD`.
- Комментарии на английском, коротко: *зачем*, а не *что*. `/** */` у публичных функций и у неочевидных UPROPERTY
  (такой комментарий виден как подсказка в редакторе). Очевидное не комментировать.
- Форматирование по `.clang-format` в корне проекта (табы, фигурные скобки на новой строке).
- Никаких предупреждений компилятора в коммите.

## 5. Имена ассетов в редакторе
`BP_` Blueprint · `DA_` Data Asset · `DT_` Data Table · `WBP_` виджет · `M_` материал · `MI_` инстанс материала ·
`SM_` статичный меш · `SK_` скелетный меш · `T_` текстура · `NS_` Niagara · `S_`/`SC_` звук/cue ·
`IA_` Input Action · `IMC_` Input Mapping Context · `L_` уровень (карта) · `ST_` String Table · `FNT_` шрифт (Font) · `FF_` начертание (Font Face).
Все ассеты проекта внутри `Content/TD/`.
